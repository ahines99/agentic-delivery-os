# Protected authored-fixture import

`import_synthetic_example(example, *, artifacts, construction_revision, image, budget, issuer,
issued_at, expires_at, reviewers)` freezes a `SyntheticExample` into a caller-owned protected
artifact store. It returns `ImportedSyntheticExample`: the example ID, full authoring artifact,
preparation request, authorization artifact and task artifact. The result contains references
only, with `purpose="SYNTHETIC_VALIDATION"`; it has no admission or execution capability.

The full authoring artifact contains evaluator-private expected decisions and reference code.
`SyntheticTask.authoring_artifact` binds those exact authoring bytes into the task digest;
synthetic provenance and usage authorization carry the same required digest. This also
authorizes only the exact supplied subject prose; a caller cannot
substitute unrelated subject instructions after authorizing the safe executable fixture.
Expected decisions are never copied into task fields, review subjects or supporting documents.
The importer preserves supplied authoring; it cannot prove that arbitrary free text is free of
semantic answer leakage, so the trusted authoring boundary remains necessary.

The importer stores source, oracle, reference snapshot, strict patch, local fixture-rights text,
license evidence, synthetic provenance and authored-reference provenance only in that protected
store. The source must contain substantive `FIXTURE_RIGHTS.txt` text. Its license identifier is
`LicenseRef-Project-Owned-Internal`, without a public redistribution or historical license claim.
Construction revision identifies fixture-construction code, while snapshot digests identify
generated bytes. Caller-supplied reviewer identities remain unchanged.

Before writing, it validates contracts, source/path bounds, supported low-risk execution task,
separate inert subject repository, explicit pytest nodes, rights text, source/oracle separation,
strict reference patch reconstruction and preserved tests/control/rights files. All generated
artifacts are staged in bounded memory and all authorization fields and time-window ordering
are validated first. Content-addressed writes then occur individually: an I/O failure may leave
partial immutable artifacts, but cannot return a successful import. Retrying identical inputs
is idempotent. There is no network, subprocess, model call or random identity generation.

Issuer and validity parameters record the trusted caller's explicit internal-data attestation.
The importer does not create a preparation policy, approve its own authorization, authenticate an
arbitrary Python caller or authorize spending. The controller must separately pin the returned
authorization in current policy and run `prepare_qualification` with actual current time,
configured repository, commands, image and disjoint execution scopes. A positive import alone
does not establish current permission.

`validate_imported_synthetic_example(imported, *, artifacts)` is a read-only pre-effect binding
check. It returns the protected authored example after checking task, authorization, provenance,
source/oracle/reference/patch and command identities. The result contains private authoring
data and must remain inside the protected controller; it is not a model projection.

`materialize_synthetic_subject(imported, anchor_input_artifact, *, artifacts)` freezes an inert
`CalibrationReviewSubject` and returns its protected artifact digest. It checks the exact
imported task and authored source/oracle against the supplied safe execution anchor, including
commands, node identities, provenance and immutable baseline. It copies only the authored
subject specification and six supporting documents; private expectations/reference code remain
in evaluator storage. A high-risk negative review subject never becomes the executed task.

This helper does not authenticate runtime completion from artifact bytes. The controller must
first validate the actual metered runtime ledger and materialize the qualification input through
the runtime validator. Structural helper tests deliberately use labelled non-runtime fixtures;
they establish binding and projection boundaries, not real execution or calibration results.
Neither importing nor materializing a subject admits a historical campaign task.
