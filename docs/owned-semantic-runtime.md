# Actual checks for owned semantic calibration examples

`OwnedSemanticRuntime` executes the five original subjects from
[semantic scoring examples](semantic-scoring-examples.md) without constructing
historical qualification or campaign authority. An ambiguous authored requirement
can be useful for development calibration while remaining ineligible for a historical
benchmark. These are distinct purposes.

The trusted controller supplies an exact finite authorization and a current policy
allowlisting its digest. Each request binds one subject artifact and immutable image.
Protected subject/output stores and the worker scope must be disjoint; a SQLite
evaluation ledger cannot reside in the worker scope. The runtime never reads the
separate expected findings or diagnostic counterexamples and has no model operation.

Each dedicated preparation account executes exactly three fixed operations: isolation
preflight, candidate acceptance and unchanged regression. The baseline source is
retained in the subject but explicitly **not executed** by this preparation. The
fixed selectors are `tests/test_batches.py::test_examples` and
`tests/test_existing.py::test_input_unchanged`. Candidate, oracle, commands, collected
nodes, collector nonce, image and operation identity bind the actual receipts.
Failed, skipped, incomplete or substituted checks stop before the next stage. Passing
the intentionally incomplete oracles cannot establish semantic correctness.

Worst-case infrastructure is reserved before each effect. Measured duration includes
the runner's cleanup and is priced using the grant's recorded estimate. Unknown
operations keep their reservation and cannot be reissued. Exact settled stages can
resume without another operation; a changed request or grant cannot reset an account.
Policy and deadlines are checked during active work. A later read-only consumer can
validate a completed chain at immutable ledger timestamps while requiring the current
data-use policy; this does not extend the original execution deadline.

Output is `EXECUTED_NOT_CALIBRATED`, with `admitted=false`, zero model calls and
`baseline_executed=false`. The consumer reconstructs all three settled operations,
exact actual receipts and costs from the owning ledger. No supplied boolean, digest
or authored expected answer can substitute for that chain. This module does not
assemble scorer contexts, call models, calibrate a scorer, admit a historical task,
grant campaign spending or report strict success.

The owned test scope passed twenty-five controlled authority/accounting/tamper
cases and five actual Docker cases (23.70 seconds) against the pinned development
image. Actual cases ran all three operations and verified cached resume left each
account unchanged. Controlled reports prove named validator behavior only; the
five real executions establish passing finite examples, not general candidate
correctness, semantic calibration or a historical benchmark result.

Independent review found and corrected a race in completed-evidence consumption:
a final refresh must still return the original grant and binding, not a newly
approved replacement. Five focused regressions cover this race, original reservation
columns and binding-checkpoint chronology. All five passed independently. A final
chronology test uses a past timestamp after execution to isolate the ordering rule.
